# SlayTheCraft v0.0.3 实施计划

本轮内容来自实测反馈 + 新需求。先修两个 bug，再按 W1–W5 分阶段推进（每阶段都要编译通过、
自检全绿、给出可执行的游戏内验收步骤）。

## 0. 本轮的 bug 修复（已随 v0.2.3 一起做）

| # | 反馈 | 处理 |
| --- | --- | --- |
| 1 | 按 ESC 直接退出战斗会让敌人一直定在原地 | 根因：ESC 以前是"本回合不再弹出界面"，而结束回合只能在界面上点 → 战斗被卡死、敌人永远保持冻结。现在 ESC 改成**暂时收起**（4 秒后自动弹回），并新增**「放弃战斗」（两步确认）**作为显式离开方式；另外给被冻结的实体写了 `stc_locked` 标记，实体再次加入世界时若已无对应战斗会自动解锁（覆盖服务器崩溃把 `NoAI` 存进存档的情况） |
| 2 | 小标题位置显示异常、文字溢出屏幕 | 战斗界面所有自绘文字按可用宽度裁剪（回合/血量、敌人名字与意图、选目标提示）、奖励 HUD 不再出现负坐标、行动栏摘要截断到 110 字符 |

## 1. W1 效果系统重做 + 状态可见性

### 需求

* 虚弱：可累加，X 层 = X 回合内攻击伤害 **−25%**（不再是"每层 −1"）
* 易伤：可累加，X 层 = X 回合内受到的伤害 **+25%**（不再是 ×1.5）
* 新效果 **活力**：下一张牌增加等于活力层数的伤害（参考原版）
* **伤害 vs 失去生命值**分离：伤害可以被格挡抵消；失去生命值直接扣血、无视格挡
* 状态可见：敌人效果显示在意图框下；自己的效果显示在**药水栏左边**（多行）
* 卡面数值随状态实时变化（虚弱2 → 打击从"6 点伤害"变成"4 点伤害"）

### 实现

* `Combatant`：`weak`/`vulnerable` 语义改为"剩余回合数"，新增 `vigor`；每回合结束时两者各 −1
* `CombatContext.previewDamage`：`(基础+力量) → 虚弱 ×0.75 → 易伤 ×1.25`，每步向下取整
* 新增 `CombatContext.loseHp(...)`（无视格挡）；灼烧/凋零/中毒处决改走它
* 活力：出牌前若为攻击牌且活力 > 0，把活力加到该牌的**第一次**伤害上，然后清零
* 新增纯逻辑 `core/CardPreview`：把卡面里的"造成 N 点伤害 / 获得 N 点格挡"替换成当前数值
  （解析卡面文本，找不到就退回原文并追加"当前：…"，不会因为文案改动而算错）
* `BattleView`：`HandCard` 增加 `description`；`EnemyView` 增加 `statuses`；新增自己状态的逐条列表
* 客户端：卡面渲染用服务端算好的描述；敌人状态画在意图下面；自己的状态画在药水栏左侧（换行）

## 2. W2 状态牌（新卡牌类型）

新增 6 张**状态牌**（`CardType.STATUS`，不可打出 / 或打出后消耗），由怪物塞进手牌、弃牌堆、抽牌堆：

| 牌 | 费用 | 效果 |
| --- | --- | --- |
| 虚空 | — | 抽到时本回合费用 −1；不能被打出 |
| 粘液 | 1 | 抽一张牌；消耗 |
| 灼烧 | — | 不能被打出；回合结束时若在手中，对你造成 4 点伤害（可被格挡） |
| 晕眩 | — | 不能被打出；虚无 |
| 毒液 | 1 | 回合结束时若在手中，对你造成 4 点伤害 |
| 呼唤 | 1 | 回合结束时若在手中，你**失去 5 点生命值**（无视格挡） |

实现：`Card` 增加"不可打出 / 抽到时 / 回合结束时"三个钩子；`CardRarity.STATUS`（不进任何卡池）；
给一个怪物意图（例如史莱姆/女巫）加"塞状态牌"，并提供 `/stc status card <id>` 调试入口。

## 3. W3 角色系统：初始遗物 + 详情页 + 新角色

* 三个原版角色的**初始遗物**：铁甲战士 = 燃烧之血（已有）、静默猎手 = 蛇之戒指（战斗开始抽 2）、
  故障机器人 = 破损核心（战斗开始生成 1 个闪电球，依赖 W4）
* 角色选取界面点角色卡 → **详情页**：头像、角色描述、初始牌组、初始遗物（图标 + 描述）
* 新角色 **叛逃掠夺者**：头像为"左眼闭合 + 伤痕"的掠夺者（程序化绘制）；
  初始遗物 **臂弩**（图标十字弩）：战斗开始时把一张【箭在弦上】加入手牌
  （0 费无色状态牌：获得活力 4；任何地方都买不到）
* 新卡：专注射击（2 费 7→9 伤害）、寻找掩体（2 费 9 格挡 + 下回合 5 格挡；升级 11+7）、
  翻滚（1 费 获得 2 敏捷、消耗；升级去掉消耗）、烟雾弹（1 费 敌人 −2 力量、自己 +2 力量；升级费用变 0）

* 需要的新引擎能力：`nextTurnBlock`（下回合获得格挡）、升级改变费用/关键字（升级表已支持）

## 4. W4 充能球（故障机器人）

* 球位（默认 3）：获得的球排在空位上；满位再获得 → **激发**最前面那颗
* 回合结束时依次触发每颗球的**被动**
* 闪电球：被动 3 点伤害（随机敌人）；激发 8 点伤害
* 冰球：被动 2 点格挡；激发 5 点格挡
* 世界内渲染：**腰部环绕**的一圈方块 —— 空位 = 标靶、冰球 = 蓝冰、闪电球 = 黄色蛙鸣灯
* 卡牌：电击（生成闪电球）、冰球（生成冰球）、双重释放（激发最前面那颗 2 次）

## 5. W5 篝火选项（含多人等待）

* 三个选项，一次只能选一个：**锻造**（升级一张卡）/ **愈合**（回复 25% 生命）/
  **包扎**（多人：为你选中的队友回复 25% 生命）
* 多人：所有同队玩家都进入篝火准备界面之后才能进行事件，界面显示"已进入 / 未进入"名单
* 计数规则：什么都不选就退出 → **不计次数**；只要有人已经选择，其他人即使没选就退出也**计入次数**

## 9. v0.2.4：Curios 饰品注册修复（阻塞性 bug）

### 症状

所有"必须携带【卡牌收纳包】"的判定全部失败：界面打不开、开战被拒。

### 根因（查了 Curios 9.5.1 的源码）

Curios 9.x 的槽位与物品资格由三件事决定：

1. **槽位定义**：数据包 `data/<modid>/curios/slots/<槽id>.json`（Curios 自带 charm / ring / … 十个）；
2. **物品标签**：`curios:<槽id>`（`validators: ["curios:tag"]` 的校验器就是读它）—— 我们**写了**；
3. **饰品能力**：`CuriosCapability.ITEM` 只挂在"实现了 `ICurioItem` 的物品"或"用
   `CuriosApi.registerCurio(item, curio)` 注册过的物品"上（`Curios.java#registerCaps` 里逐个物品判断）。

我们三样里只做了第 2 样 —— **收纳包没有饰品能力，所以根本放不进饰品槽**，于是所有携带判定失败。

### 修复

* `CuriosCompat.registerBinder(...)`：调用 `CuriosApi.registerCurio(binder, ...)`，
  其中 `canEquipFromUse()` 返回 **false**（右键仍然打开收纳包界面，装备靠饰品栏拖拽，两条路径不抢）；
* `BinderResolver.registerCuriosItem()`：**只在 Curios 已加载时**才触碰 Curios 类型（保持软依赖约定），
  由主类在 mod 总线的 `RegisterCapabilitiesEvent` 里调用；
* 新增**专属槽位** `stc:binder`：`data/stc/curios/slots/binder.json`（size 1、图标复用 Curios 的护符槽图标、
  `validators: ["curios:tag"]`、order 210）+ 物品标签 `data/curios/tags/item/binder.json`；
  原来的 `curios:charm` 标签保留（护符槽也能装，两个槽任选其一）；
* 失败提示改成可执行的：`binderLocation` 会写"背包里（未装备：请把它放进饰品栏的『卡牌收纳包』或『护符』槽）"，
  并追加 `equipHint()`（默认按 C 打开饰品栏）；物品 tooltip 也改成同样说法。

### 验证

* 新增自检套件 **`CuriosSlotCheck`（12 项）**：槽位定义存在/合法（`curios:tag` 校验器、size ≥ 1、图标与排序齐全）、
  两个物品标签都包含收纳包且不是 `replace: true`，并**直接读源码**确认
  "主类在 `RegisterCapabilitiesEvent` 里调用了 `registerCuriosItem`"、"`CuriosCompat` 里确实调用了
  `CuriosApi.registerCurio`" —— 这条正是本次 bug 的回归守卫；
* 全部 9 套自检合计 **284 项**通过（引擎 318 项，总计 **602 项**）；`compileJava` / `compileTestJava` /
  `processResources` / `runData`（日志里 Curios 9.5.1 正常加载）全绿；版本号 **0.2.4**。

**仍需游戏内验收**：进世界后把【卡牌收纳包】拖进饰品栏（按 C）→ 应能放进
「卡牌收纳包」槽或「护符」槽；装备后按 B 应能打开界面；没装备时提示会告诉你放进哪个槽。

## 11. v0.2.6：收纳包触发条件重做 + 页面约定

反馈原文："你仍然没有为 Curios 创建栏位。因此，重新制作这方面的触发条件：玩家主手手持来代替
原来需要装到饰品栏位才能执行的操作。重开页面应该为新建页面再显示重开选项。以后，默认任何有子页面的
内容，其母页面的查看详情等引导都默认新建页面 UI 显示子页面，以防出现文本堆叠等问题。"

### 1. 携带判定改成"手持"

* `BinderResolver.hasBinder`：**主手或副手拿着**收纳包即算携带（装了 Curios 且确实装备在饰品槽里也算，
  那条路保留但不强求）；只有"在背包里没拿出来"不算，提示会写明"背包里（没拿在手上）"+"拿在主手或副手即可"。
* 删除配置项 `requireCurios`（它原来的语义是"必须放进 Curios 饰品槽"）；Curios 的注册代码与
  `data/stc/curios/slots/binder.json` 槽位定义保留（有能力时装上也照样生效，不影响手持玩法）。
* 物品 tooltip 改成"拿在手上随身携带（装了 Curios 也可以放进饰品槽）"。

### 2. 重开改成独立页面

新增 `client/RestartConfirmScreen`（独立的新页面：确认重开 / 取消，两个按钮各自回到尖塔入口），

### 21.1 第一回合被跳过 —— 找到并修掉了根因

* **根因**：`BattleStandardItem.use(...)`（右键**空气**）在战斗中会直接 `CombatManager.endTurn(...)`。
  而"对着怪物按住右键开战"时，原版 `Minecraft.startUseItem` 会**每 4 tick 重复一次物品使用动作**；
  开战那一瞬间战斗已经开始，于是紧接着的重复动作就命中了"结束回合"分支 ——
  **第 1 回合在玩家看到界面之前就被结束掉了**。这解释了两个反馈：
  "第一回合被跳过，无论哪个角色"，以及"（机器人）战斗开始时会直接触发充能球结算"
  （回合结束本来就会触发球的被动）。
* **修复**：`BattleStandardItem` 的右键空气**不再结束回合**，只给一句提示（告诉玩家用界面按钮 / R / 指令）。
  同时给界面补了 **R = 结束回合** 的快捷键。
* 上一轮加的"开局状态"服务端日志保留：`战斗开始：第 N 回合 / 阶段 / 行动玩家 / 能量 / 手牌 / 存活敌人`。

### 21.2 敌人信息栏强制对齐

  再用相机（`Camera` 的位置/朝向）+ 实际 FOV 与窗口宽高比把世界坐标**投影成 GUI 横坐标**。
* `BattleScreen.enemyPanelXs(view)` 用这个投影决定每个信息栏的 x（投影失败才退回"平均铺开"），
  并且**绘制与命中判定共用同一份坐标**（对齐之后依然点得准）。

### 21.3 放弃战斗 = 直接死亡

* 「放弃战斗」按钮从右上角移到**药水栏右边**；二次确认的提示改成需求原文
  "确认放弃吗？这将直接杀死你！"，并画一个**红色高亮框**。
* `CombatManager.quit` 现在会：解散战斗（解锁敌人、写回独立生命值）→ 标记本局结束 → `player.kill()`

## 23. v0.4.4：怪物以战斗 UI 栏位为基准对齐

### 需求原文（本轮）

> 存在的问题：让怪物实体以战斗UI栏位置为基准对齐，而不是让UI和实体对齐。UI的等级更高，以此显得UI整齐。

### 23.1 方向反过来了：UI 是基准

* v0.4.2 我做成"UI 跟随实体"（把实体的世界坐标投影成栏位横坐标）。反馈要求反过来：
  **栏位固定在屏幕上整齐等距**，让**怪物**去对齐栏位。
* 因此：
  * 客户端 `BattleScreen.enemyPanelXs` 回到"等距布局"（并且删掉了跟随实体用的 `BattleEntities`）；
  * 新增客户端 → 服务端的 `BattleAlignPayload`：把每个信息栏的**归一化中心**（0..1）、
    垂直 **FOV** 与窗口**宽高比**发给服务端；
  * 服务端 `CombatManager.alignEnemies` 反算世界坐标并逐只传送（沿用 `PlacementHelper` 的安全落点：
    算出来的位置不安全就留在原地，不会硬塞）。

### 23.2 反算公式（放在 core，可离线自检）

`EnemyFormation` 新增（v0.4.4 段）：

```text
归一化横坐标  u = 0.5 + lateral / (2 · depth · tan(fov/2) · aspect)
进深         depth = standoff · cos(pitch) + eyeHeight · sin(pitch) + cameraDistance
横移比例     lateralScale = 2 · depth · tan(fov/2) · aspect
⇒ lateral = (u − 0.5) · lateralScale          （正值 = 屏幕右侧）
```

* `depth` 与横向偏移**无关**（屏幕右方向 ⊥ 视线），所以所有怪物都摆在同一进深、只按横向区分 ——
  这样投影才"只由横向偏移决定"，与公式一致。
* 进深参数取服务端已知的量：对峙距离（配置）、俯视角（房主当前 XRot，战斗中客户端会压在
  `battleCameraPitch` 上）、眼睛高度 1.62、第三人称相机距离 4.0（原版固定值）。
* 屏幕右方向按 MC 约定取 `(-cos yaw, -sin yaw)`（yaw 0 面向 +Z 时向右是 -X），
  自检里专门断言了"左→右顺序与世界横向顺序一致、不是镜像的"。

### 23.3 触发时机

* `ClientBattleState` 新增 `battleId`（每开一场 +1）；`BattleScreen` 在绘制前调用 `ensureAligned()`：
  **每场战斗对齐一次**，并且当**窗口尺寸或敌人数量变化**时重新对齐（改 GUI 缩放 / 拉窗口后怪物会重新站好）。
* 多人时记录房主（`BATTLE_HOSTS`），统一以房主视角对齐；每次对齐会写一条日志
  `按 UI 栏位对齐了 N 只敌人（fov … / 宽高比 … / 横移比例 …）`。

### 验证

* 引擎自检 641 → **657 项**（v0.4.4 新增 16 项）：进深/横移比例为正、**往返一致**
  （中心 → 世界横向偏移 → 投影回中心）、中间那只在正前方、屏幕右半边的栏位对应的世界位置确实在屏幕右侧、
  左→右顺序不是镜像、三只怪同一进深、宽高比越大横移越大、单敌人与空输入边界、屏幕右向量约定。
* 9 套 MC 自检保持 **367 项**；合计 **1024 项**；
  `compileJava` / `compileTestJava` / `processResources` / `runData` 全绿；版本号 **0.4.4**。

**仍需游戏内验收**：按 README §45 走一遍（栏位等距不乱跑、怪物站在栏位正下方、点选仍准、

## 33. v0.4.6.6（续）：BOSS 音乐「放文件就生效」+ 随包音乐

### 33.1 为什么要做约定事件名

第 31 节留下的问题是：作者想换 BOSS 音乐必须**改代码**（`StcApi.registerBossMusic`），
而这轮的原始需求是「素材留接口给我自定义修改和开发」——
"接口"如果每次都要我在 Java 里加一行，那就不算接口。

于是定义一个**纯资源即可生效**的约定：

| 层号 | 文件（打包路径） | 声音事件（约定） |
| --- | --- | --- |
| 1 | `assets/stc/sounds/boss/floor_1/floor_1.ogg` | `stc:boss_music_floor_1` |
| 2 | `assets/stc/sounds/boss/floor_2/floor_2.ogg` | `stc:boss_music_floor_2` |
| 3 | `assets/stc/sounds/boss/floor_3/floor_3.ogg` | `stc:boss_music_floor_3` |
| n | `assets/stc/sounds/boss/floor_<n>/floor_<n>.ogg` | `stc:boss_music_floor_<n>` |

* `StcApi.bossMusicConvention(层号)` 生成事件名；`StcApi.bossMusicFor(层号)` =
  "登记优先 → 约定兜底"（`bossMusic(层号).orElseGet(...)`）；
* 客户端 `BossMusic.start` 从 `StcApi.bossMusic(floor)` 改成 `StcApi.bossMusicFor(floor)`，
  于是"没登记 = 不播"变成"没登记 = 试约定事件名"。找不到事件时原来的"只警告一次"逻辑兜住；
* 于是**放对文件就有音乐，一行代码都不用写**；想换文件名 / 换命名空间（或直接绑
  `minecraft:music_dragon`）才需要 `registerBossMusic`。

### 33.2 作者提供的 3 首曲子（已随包）

作者把三段 mp3 转成了真正的 Ogg Vorbis（前 4 字节 `OggS` + identification header 含 `vorbis`）：

| 文件 | 大小 |
| --- | --- |
| `floor_1.ogg` | 1,823,978 B |
| `floor_2.ogg` | 2,025,423 B |
| `floor_3.ogg` | 3,195,067 B |

* `src/main/resources/assets/stc/sounds.json` 是**新加**的（原来根本没有这个文件），
  三个事件都指向 `stc:boss/floor_<n>/floor_<n>` 并带 `"stream": true`；
* 工作区同步保留真源：`assets/sounds/boss/floor_<n>/floor_<n>.ogg`，

* jar 因此从 ~700 KB 增到 ~7.7 MB —— 这是随包音乐的正常体积，不是漏进了临时文件。

### 33.3 两个"坑"写进接口层

1. **Minecraft 只解码 Ogg Vorbis**：mp3 / wav / m4a / flac 放进去不会响，也**不会报错**；
2. **`sounds.json` 必须在 `assets/<命名空间>/sounds.json`**，放进 `sounds/` 子目录里

  绝不静默复制；以 `_` 开头的目录（`_originals/`）不导入也不报警；
* 第 18 套自检 `SoundAssetCheck` **41 项**把位置、事件名、引用路径、磁盘文件、编码、脚本护栏全部钉死。

## 35. v0.4.6.8：三个问题修复 + 状态机移交

### 35.1 BOSS 战斗打不开（回归缺陷）

v0.4.6.7 把"**开战即记账**"写进 `ProgressState.bossesFought`：本意是"每只 BOSS 只能触发一次战斗"，
实际效果是**放弃 / 战败一次之后这一层的 BOSS 永久打不了**（`challengeBoss` 直接返回
"都已经触发过战斗了"）。

修法（两层保险）：

1. 记账时机从"开战"改到"**打赢**"：`grantBossProgress` 里先 `withBossFought(bossIdOf(mob))`
   再 `recordBossDefeat()`；于是"每只 BOSS 只能打赢一次"仍然成立，但打不过可以反复挑战。
2. 旧存档自愈：`challengeBoss` 发现"本层所有 BOSS 都被记成打过、但 `bossDefeated(层) == false`"
   时，调用新增的 `ProgressState.clearBossesFought()` 清空记录并放行，同时给玩家一句提示。

自检补 2 条：`clearBossesFought()` 能清空；`byEntityId("stc:lightning_creeper") == null`。

### 35.2 图鉴详情页的小图标变成四个

`IconFit.draw` 用的是 8 参 `blit(texture, x, y, u, v, w, h, texW, texH)` —— 这个重载里
`w/h` 同时是"目标尺寸"和"UV 采样区域"，于是 32×32 的框画 18×18（或 16×16）的贴图时会采样 0..1.78，
GL 平铺把贴图画成 **4 份**（用户看到的"四个效果图标"），并且看起来像"异常缩放"。

改成 10 参重载：`blit(texture, x, y, w, h, 0, 0, texW, texH, texW, texH)` —— UV 固定整图，
目标尺寸单独给，等比缩放 + 居中，不再重复。

### 35.3 闪电苦力怕 → 移除；机制交给旋风人

* 删：`FloorBoss` 的第 4 只一层 BOSS + `LIGHTNING_CREEPER_ID` 常量、`Faction` 的成员、
  `MobIntents` 的虚拟档案与"带电的苦力怕"特判、`MobTiers` 的 BOSS 判定、

  （`MobIntents.VIRTUALS` 这套"虚拟怪物"机制保留，注释写明当前为空、留给以后同类需求。）
* 给：`register(EntityType.BREEZE, new Profile("旋风人", 蓄能5回合, hpLock=true, loopFrom=1, ...))`
  —— 蓄能 15 / 12 伤+3 / 15 伤+3 / 力量 1+3 / 回血 15+10，之后循环第 2~5 回合；
  血量即将低于 1 进入【晕眩】，下回合结算蓄能后消散（生命仍是 224）。

### 35.4 图鉴微调

### 重构方案（要做"增幅器：每回合首次激发额外触发一次"）
1. 把 1700-1743 的方法体**整体**改名为 `private boolean doEvoke(Combatant owner)`（签名换名即可，内部不动）；
2. 新写一个同名包装：
   ```
   public boolean evokeOrb(Combatant owner) {
       if (owner.evokeBonusOnce() && !owner.evokeUsedThisTurn()) {
           owner.markEvokeUsedThisTurn();
           boolean first = doEvoke(owner);
           boolean second = doEvoke(owner);
           return first || second;
       }
       return doEvoke(owner);
   }
   ```
3. `Combatant` 加三个成员：`boolean evokeBonusOnce` / `boolean evokeUsedThisTurn` +
