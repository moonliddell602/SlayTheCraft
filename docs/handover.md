## 2. 常用命令（Windows PowerShell）

```powershell
$env:JAVA_HOME="D:\itheima\environments\openjdk21"; $env:Path="$env:JAVA_HOME\bin;$env:Path"
cd "D:\作品\MOD设计\SlayTheCraft"

# 全量自检（引擎 + 20 套 MC 套件）：这是每批必跑的一步
powershell -ExecutionPolicy Bypass -File tools\run-checks.ps1
powershell -ExecutionPolicy Bypass -File tools\run-checks.ps1 -Only Chat      # 只跑匹配的套件
powershell -ExecutionPolicy Bypass -File tools\run-checks.ps1 -EngineOnly     # 只跑引擎
powershell -ExecutionPolicy Bypass -File tools\run-checks.ps1 -SkipEngine     # 只跑套件

# 编译（本机无外网，必须 --offline）
.\gradlew.bat compileJava compileTestJava --offline --console=plain

# 出 jar 并复制到 dist
.\gradlew.bat build --offline --console=plain
Copy-Item "build\libs\stc-<版本>.jar" "dist\stc-<版本>.jar" -Force

# 导出遗物全表/统计 → docs/relics-export.md + .csv（.md 里还有 CSV 的说明；不需要 MC 类路径）
.\gradlew.bat compileTestJava --offline --console=plain
java "-Dstdout.encoding=UTF-8" -cp "build\classes\java\main;build\classes\java\test" com.slaythecraft.tools.ExportRelics
```

> ⚠️ **必须用 `powershell`，不要用 `pwsh`**。`tools\run-checks.ps1` 含中文，靠 **UTF-8 BOM**
> 让 Windows PowerShell 5.1 正确解码；`pwsh` 会把它当 GBK 读成乱码，报出一堆假的语法错误
> （`Unexpected token '}'`）。
>
> 🔴 **改 `tools\run-checks.ps1` 时务必确认 BOM 还在**（我 v0.5.0.4 就用编辑工具把 BOM 弄丢过一次，
> 脚本直接崩）。检查/恢复：
> ```powershell
> $p="tools\run-checks.ps1"; $b=[IO.File]::ReadAllBytes((Resolve-Path $p).Path)
> if(-not ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)){
>   [IO.File]::WriteAllBytes($p, [byte[]](0xEF,0xBB,0xBF) + $b) }
> ```
> 同一个坑：`Set-Content -Encoding UTF8` 在 PS 5.1 下也会**加** BOM，会让 `javac` 报
> "非法字符: '\ufeff'"。写 Java 临时文件要用
> `[IO.File]::WriteAllText($path, $code, (New-Object System.Text.UTF8Encoding($false)))`。
>
> **Gradle 需要工作区外的 `C:\Users\HP\.gradle` 写权限**；在被沙箱限制的会话里，
> `gradlew` 会因 `.lck 拒绝访问` 失败（不是脚本的问题）。

## 3. 每次加卡的**已验证配方**（成功 13 次）

1. **一批 3 张**（试过 7/8 张，两次都在 `初始化程序中出现的非法内容` 上来回回滚，白烧两轮）；
2. 每张卡：**类级 `public static final Card XXX = register(new Card(...))` + 它自己独立的 `static { upgrade(...) }`**；
3. **插入点**：`CardLibrary.java` 里 `5 + self.boltBonus(), "「弩箭射击」"` 那一行之后（单行锚点，LF/CRLF 都能匹配）；
4. 插完**立刻编译**（`Compile-Core`），失败就**整段回滚**（把改动前文本写回）；
5. 自检用**新增方法 + 在 `run(...)` 调用清单里加一行**（不要往已有测试方法里按锚点插断言，会撞已有局部变量名）；
6. 跑自检时**打印全部 `^FAIL`**（过滤会把真正的失败藏掉）；
7. 断言涉及"同一张牌打两次 / X 费" → **先补能量**（我在这上面栽过两次）；
8. 卡牌 id **先查重**（`docs/v0.0.3-plan.md` §40 是清单体检结果），常量名也要查（同名就加 `_CARD` 后缀）；
9. 每张卡**必须同批写强化版**（自检有"每张非状态/非诅咒牌都要有强化版"这条）。

1. **注册表是"覆盖层"，不是"唯一来源"**。内置 246 张卡仍然在代码里 —— 因为引擎自检必须在

   所以数据包能组合已有行为，但造不出新机制（要造新机制得先在代码里登记一条行为）。

   * `upgradeLevel(card)` 反查档位（比较时**忽略附魔**：带附魔的手牌是 `withEnchantments`
     造出来的新对象，引用比较会认不出来），`nextUpgradeOf(card)` 给"本场战斗升级"用。
2. **E14 死亡爆炸**（【尸体爆炸】）—— 没有单开"死亡广播"：标记记在**敌人身上**
   （`Combatant.corpseExplosion`），在 **`checkBattleEnd()` 最前面**结算。这样"所有击杀路径
   都会走到"是白拿的：伤害、中毒、凋零、荆棘、状态牌自伤一个都不漏。带防重入闸
   （`detonatingCorpseExplosions`），所以"A 炸死 B、B 也带着标记"会**连锁**。
3. **`PlayerState.pendingPotions`**（【炼金】）—— 药水是**档案层**数据
   （`PlayerCardData.potions`），零 MC 依赖的引擎碰不到它。所以引擎只**记账**，
   MC 层在**这张牌打完之后**立刻兑现（`CombatManager.grantPendingPotions` → 随机一瓶 +
   槽位满了就明说），这样**本场战斗就能用上**；`settleBattleExtras` 里另有一道兜底。
4. **`PlayerState.toolsOfTheTrade`**（【行业工具】）—— 回合开始按层数各来一次"抽 1 弃 1"，
   位置在**正常抽牌之后**（原版也是手牌抽齐了才触发）；弃哪张复用已有的 `discardOrder` 贪心。
5. **`PlayerState.wellLaidPlans`**（【计划周全】）—— 回合结束**额外保留 N 张**，
   在 `discardHand` 里与【保留】关键字并存（留**费用最高**的 N 张）。

另外**顺手修掉两个老毛病**（都属于"以前只有 0/1 两级，所以写死了"）：

* **`BattleView.HandCard.upgraded`（boolean）→ `upgrades`（int 档数）**：手牌快照以前只发
  "有没有强化过"，所以**所有**强化过的牌在手牌里都会用基础版的名字显示（数值由服务端算好的
  `description` 顶着，所以一直没被注意）。现在发档数，客户端 `resolve(id, upgrades)` 取对那一档。
  老快照没有 `upgrades` 字段 → 宽容解码成 `0 / 1`（`BattleViewCheck` 已覆盖往返）。
* **本场战斗升级（【军备】/【军备+】）**：从写死的 `resolve(card.id(), 1)` 改成
  `nextUpgradeOf(card)`（**从当前档位上一档**），并保留附魔 —— 否则手里 +3 的灼热打击会被
  "升级"回 +1（**倒退**）。

#### ⚠️ 已知偏差（本批新增）

* 【行业工具】的"弃 1 张"与【计划周全】的"保留 N 张"在原版是**玩家自己选**，
  本模组**没有为它们加选牌弹窗**，按贪心自动决定（弃 = 状态/诅咒优先、其次低费；留 = 费用最高）。
  要改成玩家选，得给这两张牌各加一个 `CardPickKind`（回合开始/结束时的选牌窗口）。
* 【尸体爆炸】的爆炸伤害走 `takeFixedDamage`：**会被格挡吸收**，但不受力量 / 虚弱 / 易伤放大。

  （强化对照仍可看到 +1 档）；"任意次"在 `maxUpgrades` 里是 `Integer.MAX_VALUE`，实际受
  玩家金币与牌组大小限制。

#### 🐞 篝火三个 bug（一条根因）

用户："篝火能被一直使用（应该不能连续使用 2 次篝火，使用并触发效果后直接离开 UI 并计算次数）"、

**根因**：`blockReason()`（次数上限 + "不能连用"）**只在"打开界面"时查一次**，

**修法**（三处）：

1. `CampfireService.finish()` 末尾 `player.closeContainer()` —— 选完立刻离开 UI；
2. 三个选项（愈合 / 包扎 / 锻造）开头都走新的 `usableNow()`：再查一次 `blockReason`，
   不合格就**顺手关掉界面**再返回原因；
3. 客户端把"次数用完"也画出来：按钮置灰 + 红字「本层篝火次数已用完」（`stc.campfire.exhausted`）。

顺带修掉一个**潜在的双重计数**：`CampfireSession.leave()` 以前只看"别人选过没有"，
所以甲选完（已记账）→ 乙也选完 → 甲关界面时**又被记一次**。现在"自己已经选过"直接返回 false。

**文字显示不全是横截断**（不是高度不够）：底部那句提示约 30 个汉字 ≈ 270 像素，

### 4.30 v0.5.1.9（**敌怪回合不再把玩家放回世界**：整场战斗都留在出牌界面上）

用户一条 **bug**："出牌回合结束后的敌怪环节，出现了玩家可能会暂时离开战斗UI，可以按 wasd 移动和旋转视角的问题。"

#### 🐞 根因（**显示条件写窄了**，不是"移动锁失效"）

`ClientBattleState.shouldShowScreen()` 以前是：

```java
return view.active() && (view.yourTurn() || isWaitingForOthers()) && hiddenRemaining() <= 0L;
```

`yourTurn = 玩家回合 + 我还活着 + 我这一轮还没确认`，`isWaitingForOthers = 玩家回合 + 我已确认 + 有队友没确认`
—— 两个条件**都要求 `playerRound`**。于是敌怪回合（`phase = ENEMY_TURN`）两个都是 false：

```
玩家确认结束回合 → 全员确认 → 服务端进敌怪回合 → 下发的快照 playerRound=false
→ shouldShowScreen()=false → StcClientSetup 每 tick 把 screen 设成 null → 玩家掉回世界
→ 能按 wasd 走动、能用鼠标转视角（原版 HUD 又被 BattleHudHider 藏着，屏幕上一片空）
```

**修法：只要这场战斗还在（`active`），界面就不收起。** 界面顶在屏幕上本身就是原版禁止移动 / 禁止转视角的
唯一手段（已在反编译源码里核对，不是猜的）：

* `Minecraft.setScreen(非 null)` → `KeyMapping.releaseAll()` + `mouseHandler.releaseMouse()`；
* `KeyboardHandler.keyPress` 里 `flag4 = this.minecraft.screen == null`，**只有 flag4 为真才 `KeyMapping.set(key, true)`**
  → 界面开着时 WASD / 空格 / Shift 的按键状态根本不会被置位，`KeyboardInput.tick` 算出的冲量恒为 0；
* `MouseHandler.handleAccumulatedMovement` 只有在 `isMouseGrabbed()`（= 没开界面）时才 `turnPlayer()`
  → 视角也转不动。

#### 🐞 bug 根因（不是"动画代码乱写"，是**标识不稳定**）

客户端给手牌算的是**稳定键**：`HandFadeTracker.key(id, upgraded) + "#" + 第几次出现`，
例如同名两张打击是 `打击#0 / 打击#1`。这个编号**按位置重新生成**：

```
手牌 [打击#0, 火焰#0, 打击#1] → 打出第一张打击 → 服务器回来的手牌 [火焰#0, 打击#0]
差值：上一帧有 打击#1、这一帧没有 → 判定"打击#1 离手了" → 替**留在手里的那张**播了一遍打出动画
```

而真正被打出的那张 `打击#0` 已经由 `play()` 那条"跟手"的路径播过了 —— 于是看起来就是
"最后一张同名牌也跟着飞了一次"。

**修法**：把"哪张牌离手了"从**位置编号**改成**按定义计数**（同名同强化算一个定义），
并且**扣掉已经为这个定义起过的动画**（`inFlightFor(definition)`）：

```
missing = 上一帧该定义的张数 − 这一帧该定义的张数
toStart = missing − 已经为它起过的动画段数
```
* 玩家打出第一张打击：`missing=1`、`inFlight=1`（`play()` 已登记）→ `toStart=0` → **不再多播**；
* 键盘/服务端把牌拿走（没有 `play()` 登记）：`missing=1`、`inFlight=0` → 补一段动画，功能不变；
* 回合结束弃掉整手：每个定义 `missing=N`、`inFlight=0` → 整手牌照旧依次飞走。

#### ✅ 拖动打出（只改**非指向性**牌）

| 环节 | 行为 |
| --- | --- |
| 按下非指向性牌 | **只开始按住**（不再立刻出牌）；同时取消"等选敌人"的状态，屏幕中心的**打出区**亮起并给出提示 |
| 长按 ≥ 180ms（`DRAG_HOLD_MS`） | 进入拖动：那张牌跟着鼠标走（不必先移动鼠标，长按本身就算"开始拖动"） |
| 拖到打出区 | 打出区高亮；**能量不足时变红并提示「能量不足」**（这时松手不会出牌） |
| 在打出区松手 | 走原来的出牌请求（`PlayCardPayload(handIndex, -1)`），打牌动画与结算都不变 |
| 在别处松手 / 短按 | 不出牌（需求明确是"而不是单点操作"）；牌留在手牌里 |
| **指向性牌** | **不变**：仍然是"点牌 → 点敌人"（需求只点名非指向性牌） |
| 数字键 1–9 | **保留**（键盘快捷方式，不属于"鼠标单点操作"） |

**打出区几何**（`playZoneRect(width, height)`，纯函数、可断言）：水平居中、宽度 `min(190, 宽−40)`，

#### ✅ 美术：每颗充能球分开播

根因：客户端 `ClientBattleFx` 里 `ORB_DAMAGE` 走的是 `start(...)` —— 一个实体只存得下**一个**动画，

* `ORB_DAMAGE` → `enqueue(敌方, ENEMY_HURT, HURT_MS, 紫水晶钟声, …)`（电流冲击那一小声量很低，仍即时播）；
* `ORB_BLOCK` → `enqueue(自己, PLAYER_BLOCK, DEFEND_MS, 钟声, …)` —— 冰球每颗各蹲起一次、各响一声。

### 4.23 v0.5.1.3（**紧急避险卡死整局** + 战斗左侧遗物栏 + 移除「X 的回合」）

#### 🩸 恶性问题：紧急避险（`emergency_dodge`）打出后**整局锁死**

现象（用户原话）："打出后，无法放弃战斗，无法结束回合，即使使用 /kill 或退出游戏重进也无法响应。"

**根因**（一条链，我已经用自检把它钉住了）：

```
finishEnemyTurn()          ← 敌人回合收尾，此刻 phase == ENEMY_TURN
  └─ beginActivePlayerTurn()
       └─ if (state.skipTurns > 0)      ← 紧急避险挂上的"跳过下一回合"
            └─ endTurn()                 ← endTurn() 第一行：if (phase != PLAYER_TURN) return;
```

`beginActivePlayerTurn()` 里 `phase = PLAYER_TURN` 那一行在**跳过分支之后**才执行，所以跳过分支调
`endTurn()` 时 `phase` 还是 `ENEMY_TURN` —— `endTurn()` 被自己开头那道保护挡回来、**一句话都不说就返回**。
于是回合再也不推进，`phase` 永远停在 `ENEMY_TURN`：

* 出牌 → 被 `if (phase != PLAYER_TURN)` 拒绝；
* 结束回合 → 同上；
* 放弃战斗 → 服务端 `quit()` 里没有 phase 判断，玩家**确实会死**，但战斗状态照旧（`release` 之后客户端
  那份 `active` 状态仍是真），战斗界面每 tick 继续被强制打开 → 看起来就是"怎么点都没反应"。

**修法**：跳过分支在调 `endTurn()` **之前**先把 `phase` 标成 `PLAYER_TURN`（保留"这一回合直接结束"的原意，
只补上它依赖的前置状态），并写清了为什么。

**加保险（看门狗）**：`CombatContext.stalledBetweenTurns()`（敌人队列已空、战斗没结束，phase 却还停在
敌人回合）+ `resumeStalledTurn()`（强制接上下一轮，**不**递增回合数），由 `CombatManager.tick` 每 tick 兜一次。
以后任何原因造成的"回合推进断链"都不会再变成只能重启的死局，日志里会留下
`⚠ 回合推进中断（敌人队列已空，阶段却停在敌人回合）：强制接上下一轮`。

**为什么旧自检没抓到**：原来只有两条断言（获得 20 格挡 / `skipTurns == 1`）。旧代码里那句
`endTurn()` **照样不报错**，所以只有盯"推进有没有真的发生"才抓得到。现在补了 8 条：
`phase == PLAYER_TURN`、回合数走到 3、手牌重新抽好、`!stalledBetweenTurns()`，以及看门狗自身的 4 条
（用包级 `forcePhaseForTest` 人为造一个断链）。**我实测过**：把修复那一行撤掉，这 8 条里有 4 条立刻变红
（"不会卡在敌人回合 / 期望 3 实际 2 / 手牌没抽 / 留下断链"）—— 断言真的咬得住这个 bug。

### 4.16 v0.5.0.17（手牌描述模块错位 —— 真根因）

反馈："手牌的描述模块出现严重错位，严重影响游戏游玩。"（在 v0.5.0.16 上出现）

**根因：描述框太窄，而"算宽度"和"画宽度"是两份不同的算法。**

| 项 | 上一版的值 | 后果 |
| --- | --- | --- |
| 描述框**画出**的宽 | `80 − 6×2 = 68` | —— |
| 最短的正式描述「造成 6 点伤害。」 | 约 **72 像素** | **必然折行** |
| 框内高度 | 25 → 只够 **2 行** | 折行后要么挤出框、要么被 `fitScale` 缩到 0.6 |

于是一张**普通打击牌**的描述就折行 + 被缩，看起来就是"严重错位"。

**修法**（三处一起，缺一条都不成立）：

| 改动 | 变化 |
| --- | --- |
| 描述框左右内缩 | 6 → **3**（框内宽 68 → **74**，刚好 ≥ 最短描述所需的 72） |
| 描述框高度 | 25 → **33**（够 **3 行**，长描述按原大小画、不用再缩） |
| 卡图高度 | 38 → **32**（让出高度；卡图与类型带之间留 2 像素间隙） |

**最终版式**（牌高 96，各块 + 留白精确合计）：

```
y=  2 .. 12   卡名带（10）
y= 12 .. 44   卡图（32）
y= 46 .. 55   类型标签带（9）        ← 与卡图之间留 2 像素
y= 55 .. 88   效果文案框（33，内宽 74，可画 3 行）
y= 88 .. 96   底部留白（关键字居中画在这一条）
```

**自检（`CodexPagesCheck` 134 → 139 项）**新增的正是**当初漏掉的那一课**：

* 描述框内宽必须 ≥ 最短正式描述所需的 `CARD_TEXT_MIN_W = 72`；
* 描述框至少能画 2 行、宽×高足够容纳一句典型描述；
* **绘制与几何必须共用同一个函数**（`textBoxInnerW()/textBoxInnerH()`）——
  上一版的错位本质就是"算宽度"和"画宽度"各写了一份。

### 4.13 v0.5.0.14（充能球圆心与玩家精确坐标对齐）

反馈："充能球位置和玩家位置存在错位的问题。充能球的圆心应该始终为玩家当前的精确坐标。"

**根因（表现层用的坐标与模型不是同一份）**：

球环圆心原来是渲染层里手写展开的 `player.getX() + offsetX(angle)`，
而那个 `getX()` 是**当前 tick** 的坐标；同一帧里玩家模型却是用**插值**坐标渲染的
（`Entity.getPosition(partialTick)` 走 `xOld → x`）。两者在**移动中**、以及**刚被服务端摆位**时
（开战站位会把玩家移到敌人正前方）会对不上，看起来就是球环"挂在身体旁边"。

**修法**：

| 改动 | 内容 |
| --- | --- |
| 圆心变成有名字的量 | 新增 `OrbRingLayout.ringCenter(playerX, playerY, playerZ)` —— 水平方向**原样**取玩家精确坐标（`position` 的水平分量就是包围盒中心，即玩家所在那一格的中心），竖直抬到腰部 `WAIST_Y` |
| 渲染层改用插值坐标 | `OrbRenderer` 用 `Mth.lerp(partialTick, xOld, getX())`；`partialTick` 取自 `RenderLevelStageEvent.getPartialTick().getGameTimeDeltaPartialTick(false)`。现在球环与玩家模型用**同一份**坐标 |
| 屏幕投影同步修正 | HUD 悬停命中判定原本单独算了一次 `py + WAIST_Y`，现在与绘制共用同一个圆心（否则"看到的球"和"能点中的球"会错开） |

**自检**：引擎 1130 → **1137 项**，新增一节把"圆心 = 玩家精确坐标"钉死：
圆心 X/Z 必须原样等于传入坐标、圆心 Y = 脚底 + 腰部高度、
**每颗球到圆心的距离恒等于半径**（1..5 球位 × 4 种朝向 × 3 种旋转偏移全组合）、
圆心只由玩家坐标决定（与球位数无关）、源码级断言"渲染层确实用了 `xOld/zOld` + `Mth.lerp` 且走 `ringCenter`"。

⚠️ **我在这一节写错过一条断言**：最初加了"所有球位偏移的平均值为 0"，而这条不变量本身是错的
（1 颗球时它到圆心的偏移就是 `(R·cosθ, R·sinθ)`）。自检当场报红——这次是**断言错了，不是实现错了**。
已换成正确的不变量，并在 `meanOffset` 的 javadoc 里写明"它不能用来断言居中"。

### 5.3 **B4 施工图：卡牌实例 ID（引擎级重构，v0.5.6.0 起做）**

> 用户明确："B4 制作 ID"。目标是把"卡牌**定义**"（共享、不可变）与"**这张具体的牌**"
> （本场战斗唯一、可以带自己的状态）分开 —— 这样【模组改造】的"本牌费用 +1"、E5 单卡记账、
> 【布置】/【地狱之刃】的"这张牌 0 费"才真正跟着那张牌走（现在都是**按 id 共享**的近似，见 §6）。

**第 1 步（v0.5.6.0，机械改造 + 兼容层，行为不变）**

1. 新增 `combat/core/BattleCard`（保持零 MC 依赖）：
   `Card definition` + `long instanceId` + `int costDelta` + `int counter` + `boolean freeUntilPlayed`；
   实例号由 `CombatContext` 发（`nextInstanceId++`），`DeckBuilder` 建牌时逐张发号。
2. 四个牌堆（`Pile` / 手牌）内部持有 `BattleCard`；**兼容层**：
   `hand()` / `Pile.view()` 继续返回 `List<Card>`（映射出定义），新增 `handRefs()` / `refs()` 给需要身份的地方。
   → 读牌的地方（卡牌效果、`CardPreview`、`BattleView`、客户端界面）**一行都不用改**。
3. 移牌的**唯一入口**全部改成携带 `BattleCard` 本体：
   `drawCards` / `discardFromHand` / `exhaustCard` / `exhaustFromHand` / `moveHandToDrawPileTop` /
   `putOnTopOfDrawPile` / `addCardsToHand` / `transformInHand`；选牌系统 `PendingCardPick` 的候选同步改成 refs。
4. 需要"这张牌自己"的效果走 `CombatContext.playedBattleCard()`：
   E5 的 `cardCounters` / `freeToPlay` /【布置】的免费额度从"按 id"改成"按 instanceId"。
5. 自检：实例 id 在牌堆内唯一 / 洗牌与弃牌堆重洗后仍跟随 / 复制出的牌是**新实例** /
   "变化"类效果保留实例与 `costDelta`；**旧断言（按 id 的近似）逐条改成按实例**。

**第 2 步（v0.5.6.x，替换近似）**

* 【模组改造】从"同 id 的 0/1/2 费三档 + 打出时换档"改成**实例 `costDelta`**，删掉多余档位；
  【魔术技巧！】的 11 档**保留**（那是内容：每份各自减费，不是近似）。

## 7. 踩过的坑（省你重复踩）

| 坑 | 正解 |
| --- | --- |
| 双引号里套双引号写 Java 字符串 | 中文引号用「」；Java 代码用**单引号数组 + `-join "`r`n"`** 拼 |
| 两行锚点拼 CRLF 去匹配 LF 文件 | **锚点只认单行** |
| 负费用当 X 费哨兵 | `Card` 会把负费用夹成 0；改用 **id 标记集合** `registerXCost/isXCost` |
| `resolve(id, 1)` 判断"有没有强化版" | 没强化版时会**回退基础牌**；要用 `hasUpgrade(id)` |
| 卡牌 id 撞车会**覆盖别人的强化版** | 加卡前查 §40 清单 + 脚本 `IdFree` 检查 |
| 一次插 7–8 张卡 | 3 张/批；`static {}` 每张独立 |
| 自检过滤输出 | 打印全部 `FAIL` 再判断 |
| 测试"同卡两次"忘记补能量 | 先 `gainEnergy(...)` |
| 以为 `run-checks.ps1` 依赖 UTF-8 BOM | 早就不是了：脚本现在是**纯 ASCII**、靠**退出码**判定成败、正则只认语言无关的 `<n> 词 / <n> 词`。**BOM 反而是它的敌人**（丢了 BOM 的 UTF-8 会被 PS 5.1 按 GBK 读成乱码）。所以别再用 edit 工具改它、也别给它加中文 |
| 用 `pwsh` 而不是 `powershell` 跑 `run-checks.ps1` | 用 `powershell -ExecutionPolicy Bypass -File tools\run-checks.ps1`（与 §2 一致） |
| 编辑工具会把 .ps1 的 BOM 弄丢 | **对 `run-checks.ps1` 已经不适用**（它现在是纯 ASCII，丢了 BOM 也没事）。但如果哪天又往某个 `.ps1` 里写了中文，就必须保证它有 BOM，或干脆照 §4.9 的做法写成纯 ASCII |
| 用 `registerGenerated` 登记"变体卡" | 它**不进 UPGRADED**，会撞自检"每张非状态牌都要有强化版" → 变体也要补一条 `upgrade(...)` |
| 以为"每张非状态牌都有强化版"对生成牌也成立 | 生成牌的**基础定义按约定就占用 "+" 名字**（如 `BOLT_SHOT`），断言要**排除生成牌** |
| 以为 `hasStatuses()` 会自动带上新状态 | 它是一串显式字段或；**加状态必须同步改它**，否则 `statusSuffix()` 直接返回空串 |
| 以为 `dealDamage` 会自己按 `intent.times()` 结算多段 | **它只结算一次**；多段循环必须在 `executeIntent` 的 ATTACK 分支里。改多段相关逻辑前先读 `dealDamage`（我按错误假设写，把段数乘了两遍，被自检抓住） |
| 给 `Animation` 加自定义时长却忘了渲染层 | `CombatAnimLayer` 原来硬用 `BattleAnim.ATTACK_MS`，**动画自己的 `duration()` 被完全忽略**；加时长参数必须同时改渲染层读 `animation.duration()` |
| `ClientBattleFx.enqueue()` 看着像已接线 | 它**从来没有调用点**（多段攻击动画就是因此坏的）。改表现层前先 `grep` 确认"这个机制到底有没有入口" |
| 用 `combatants.size()` 算"场上第几只" | 这个列表**含已阵亡的敌人**，只增不减；要数就数 `alive()`，并给最终坐标加硬上限 |
| `Set-Content -Encoding UTF8` 写 Java 临时文件 | PS 5.1 会加 BOM，`javac` 报"非法字符: '\ufeff'"；用 `[IO.File]::WriteAllText($p,$s,(New-Object System.Text.UTF8Encoding($false)))` |
| 用 `pwsh` 跑 `run-checks.ps1` | 用 `powershell`（脚本靠 UTF-8 BOM，见 §2） |
| GUI 缩放想逐个坐标乘 | 手牌这类"整块缩放"应该用 `graphics.pose()` 以牌中心为基准 `scale`，再 `popPose`；逐个乘会把文字也搞乱 |
| 给"下移 UI"加偏移量却忘了底边距 | 手牌 y = `屏高 − 牌高 − 底边距 + 下移`；**下移 > 底边距就必然越屏**。我按 8 的底边距配 26 的下移，被 `CodexPagesCheck` 抓住。加这类偏移要同时定一条"偏移 < 底边距"的断言 |
| 改了常量但测试还报旧值 | 先确认**编译真的成功了**：编译失败时测试跑的是上一次的 class，报出来的失败全是假象（我在这上面浪费过一轮） |
| 在**静态初始化**的类里直接引用 `SlayTheCraft.LOGGER` | 会 `ExceptionInInitializerError`（`SlayTheCraft` 的静态初始化会反过来碰注册表，形成环）。`CharacterRegistry.register` 就是靠自己的静态常量初始化的，所以日志要用 try/catch 包一层（见该类里的 `log(...)`） |
| 在类里 new 出一个"卡片/面板"结构时覆盖了下一段 javadoc | 我插方法时把下面方法的 `/**` 吃掉了，编出一堆"非法字符"。插方法后**顺手看一眼后面的注释还在不在** |
| 以为 `advancement` 的 `parent` 要写**文件目录** | `parent` 用的是**进度 id**，即 `命名空间:路径`，而路径**不含** `advancement/` 那层目录。文件放在 `data/stc/advancement/stc/root.json`，它的 id 是 `stc:root`（**不是** `stc:stc/root`）。写错的话整条成就从树上掉下来（游戏里表现为"这条成就消失了"），自检里加了"父节点必须在登记表里"来拦 |
| 以为"出牌后会补抽一张" | **不会**——抽牌只在回合开始（`beginActivePlayerTurn`）。写"连打 4 张同名"这类自检时，起手手里就得有 4 张，否则打到一半没牌了 |
| 以为自检里的牌组顺序是确定的 | 抽牌堆会被**洗牌**，所以"手牌构成"不可预测。要测具体牌序就**显式投喂**（`addCardsToHand`），或把牌组做成清一色同名牌 |
| 以为 `advancement` 文件存在 = 游戏认它 | 原版 `ServerAdvancementManager` 对**反序列化失败**的进度只写一行 `LOGGER.error("Parsing error loading custom advancement {}")` 就**静默丢弃**，接着 `AdvancementTree.addAll` 会因子节点找不到父节点打印 `"Couldn't load advancements"` 并 `break`。游戏里的表现是**"根还在、其余成就整片消失"**。光用 Gson 查语法**完全拦不住**——必须按 codec 定义逐字段校验（字段白名单 / 必填项 / 精确类型 / 枚举 / 触发器白名单），见 §4.9 的 `AdvancementCheck`（419 项） |
| 想给根成就挂 `show_toast` 做"进游戏"提示 | 原版对**根**另走分支（`PlayerAdvancements` 的自动授予与可见性都判 `isRoot()`），根上的 toast 不可靠。**提示要挂在子成就上**，根只当标签页容器（原版所有自带根成就都是 `show_toast:false` / `announce_to_chat:false`） |
| 以为成就界面**左上角那行字**取自某条子成就 | 它是**根节点 display 的 title**（`AdvancementTab.title = display.getTitle()`）。所以"分支名"必须写在根上 |
| 嫌根碍事就把根的 `display` 删掉 | **不能删**：`AdvancementTab.create` 对 `display().isEmpty()` 直接 `return null`，于是**整个标签页都不生成**。（注意 `AdvancementTree` 的可见性对"无 display 的根"返回 HIDE，也是同一套约定。）原版 `data/minecraft/advancement/recipes/root.json` 确实没有 display，但那正是它不生成标签页的原因 |
| 用 `minecraft:tick` 触发"进游戏即有"的成就 | 触发器本身有效（在 56 个注册名里），但"玩家进世界后会不会恰好收到一次 tick 事件"依赖加载时序。**同时在 `PlayerEvent.PlayerLoggedInEvent` 里显式授予**（`AchievementService.grantEnteredGame`）才确定；而且显式授予要放在 `data.initialized()` 早退**之前**，否则老存档补不上 |
| 在原版源码里找"进度会不会被静默丢弃" | 去 `build/neoForm/<...>/sources.jar` 里抽 `net/minecraft/advancements/*`、`server/PlayerAdvancements.java`、`client/gui/screens/advancements/*` 直接读——比搜索"1.21 成就 不显示"快得多，而且答案确定 |
| 在裸 JVM 里跑 `Advancement.CODEC` 做校验 | 走不通：`Advancement` 的静态初始化会触发 `CriteriaTriggers` → `BuiltInRegistries` 需要 `Bootstrap.bootStrap()`，而 NeoForge 的 bootstrap 又要求 `LoadingModList`（裸 JVM 里为 null）。**自检要按 codec 定义手写复刻校验**，不要试图在自检里真跑原版 codec |
| 以为 `Bootstrap.bootStrap()` 失败后"已初始化的注册表还能用" | 也不行：`BuiltInRegistries.<clinit>` 本身就带 `checkBootstrapCalled`，未 bootstrap 时**整个类初始化失败**，之后 `ITEM`/`TRIGGER_TYPES` 全是 `NoClassDefFoundError`。所以"先 bootstrap 让它炸一半、捡剩下的用"这条路是死的 |
| 用"只有根显示"就当数据错了 | 先用**复刻验证**分辨是"数据没加载"还是"可见性过滤"：把 `AdvancementTree.addAll` + `AdvancementVisibilityEvaluator` 的逻辑手写一遍（它们不依赖注册表，裸 JVM 能跑），喂进真实的 parent 表算可见性。我这次靠它确认**可见性机制正常**，省下了乱改 JSON 的一轮 |
| 拿 `pwsh` 启动纯 ASCII 的 `.ps1` 临时脚本 | 用 `powershell`；PS 5.1 会把无 BOM 的 UTF-8 当 GBK 读，**脚本里任何中文路径/字符串都会变乱码**（`Set-Location : Cannot find path 'D:\浣滃搧\...'`）。临时脚本要么走 `[IO.File]::WriteAllText(..., UTF8Encoding($false))`，要么**别写中文、用相对路径** |
| 用 edit 工具往大文档里插章节 | 容易**吃掉下一节的标题行**（我这次把 `### 4.8` 的标题吞了）。插完立刻 `grep '^### '` 看章节号是否连续 |
| 看到 `Get-Content` 输出中文乱码，就以为文件坏了 | 那是**控制台按 GBK 解码 UTF-8**，文件本身可能是好的。判断文件是否真的损坏要用 `[System.Text.UTF8Encoding]::new($false,$true)`（throwOnInvalidBytes）**严格解码**，或直接用 read 工具看。我差点因此把 `docs/acceptance-log.md` 白重做一遍 |
| 用 `"中文…"每张…"中文"` 这种嵌套双引号的 PowerShell 字符串 | PS 会把第二个 `"` 当成字符串结束 → `Unexpected token`。中文说明里的引号一律用 `「」`，或改用单引号字符串 |
| 在 **MC 类路径自检**里碰 `BuiltInRegistries.*` / 构造 MC 注册表对象 | **会直接抛 `ExceptionInInitializerError` 并让整个套件挂掉**（裸 JVM 没有 NeoForge 的 bootstrap）。我为了验"名单里的实体都能查到"去读 `BuiltInRegistries.ENTITY_TYPE`，`CodexPagesCheck` 当场炸。想在自检里验这类事情，改成**源码级断言**（读 `.java` 文本里有没有那次调用），或把注册表校验留给游戏内验收 |
| 自检里写"读不到就 return，跳过这条断言" | 那是**假通过**：我写了个依赖 `client-extra.jar` 的断言，把 jar 名改错后通过数**纹丝不动**，说明它根本没跑。正确做法是**做不了就显式报失败并写清原因**（"未完成：需要 X"），这样"跳过"在汇总里看得见 |
| 改了断言后忘记先跑 `compileTestJava` | 编译失败时 `run-checks.ps1` 跑的是**上一次的 class**，通过数看着正常、其实验的是旧代码。改完自检先单独编译一次，或确认构建输出里没有 `错误:` |
| 负向测试才是断言的"有效证明" | 断言写完不算完：**故意制造一次失败**（把实体名改成不存在的、把 jar 名改错）确认它真的会红。这次两条新断言都是这么验的——其中一条当场暴露了自己是假通过 |
| 断言写成"我以为的不变量"而不是"真正的不变量" | 我给球环写了"所有球位偏移的平均值为 0"——**这条本身是错的**：只有 1 颗球时它到圆心的偏移就是 `(R·cosθ, R·sinθ)`，平均值当然不为 0。自检当场报红，我一度以为是实现错了。**看到断言失败先问"这条不变量真的成立吗"**，再怀疑代码。正确的不变量是"每颗球到圆心的距离恒等于半径" |
| 渲染位置用**非插值**的实体坐标 | 实体模型是用**插值**位置渲染的（`Entity.getPosition(partialTick)` 走 `xOld → x`）；而 `getX()/getZ()` 是**当前 tick** 的值。表现层的附着物（充能球、光环、粒子）如果直接用 `getX()`，移动中或刚被服务端摆位时就会"挂在身体旁边"。附着物要跟模型用**同一份插值坐标**（`Mth.lerp(partialTick, xOld, getX())`，`partialTick` 从 `RenderLevelStageEvent.getPartialTick().getGameTimeDeltaPartialTick(false)` 取） |
| 在 core 的裸 JVM 自检里用 Minecraft 的类 | `Mth` / `Vec3` / 任何 MC 类都**不在裸 JVM 类路径里**（`run-checks.ps1 -EngineOnly` 只编译 `combat/core` + 自检入口）。core 自检要读源码做"接线没断"的断言，就自己写个 `Files.readString` 的 helper（`CombatSelfTest.readSource`），别引 MC 类 |
| 改了**设计意图**却留着旧断言 | v0.5.0.15 把卡名从"卡图下沿"搬到"最上面"（按用户给的版式图），旧断言"卡名在卡图下沿之下"与设计**直接冲突**、自检报红。正确做法：改设计的同时改断言，并**在断言旁边写清"前提变了"**（我加了一句"⚠️ v0.5.0.15 起这条断言的前提变了…"）。否则下一个人会以为断言是对的，把设计改回去 |
| 把"某块内的文字 y"当成"某块的顶边" | 我把 `cardLayoutOffsets()[2]` 当成"卡名带的顶"来用，而它其实是"带内文字的 y"（带顶是 `off[8]`）——自检报红 3 条里两条是这个取值错误。**索引数组的语义要写在 javadoc 里**，别靠记 |
| 加常量时手滑删掉相邻空行 | 这轮给 `OrbRingLayout` 加常量时删掉一个空行，把下一个字段的 javadoc 挤到了同一行。编辑大块常量区之后**顺手扫一眼格式**（同类事故在"插方法吃掉 javadoc"那里也发生过） |
| 看到费用是 `0` 就以为读错字段了 | 先分清"字段读错"还是"**字段被设计成 0**"：X 费牌的 `Card.cost()` **本来就是 0**（构造器把负费用夹成 0，X 费用 id 标记集合实现）。表现层要显示「X」得查 `CardLibrary.isXCost(id)`，不能看数值 |
| 把 `CardInstance.upgrades`（**int**）当布尔用 | 它一直是 int，但 `upgrades == 0` / `> 0` 这种布尔式判定散在 `PlayerCardData` 四个方法里，于是"多重强化"卡（【灼热打击】）永远只能升一次。加多档卡时**先 grep `upgrades()`**，把所有上限判定改成问 `CardLibrary.maxUpgrades(id)` |
| 用 `resolve(id, 1)` 做"本场战斗升级" | 那是"**取 +1 档**"，不是"上一档"：手里 +3 的【灼热打击】会被"升级"回 +1（倒退）。要用 `nextUpgradeOf(card)`（它按 `upgradeLevel` 反查当前档位） |
| 以为 `Card` 定义的引用相等能当档位判断 | 带附魔的手牌是 `withEnchantments` 造出的**新对象**，引用比较 / `equals` 都会失败。档位反查要用**忽略附魔的字段比较**（`sameDefinition`） |
| 在 `checkBattleEnd()` 里做"死后触发"却不加防重入 | 死亡触发常常自己又会造成伤害 → `dealDamage` → `checkBattleEnd` 递归。要加一个 `boolean` 闸（我这里叫 `detonatingCorpseExplosions`），并在结算后**再查一次 `phase.isOver()`**，否则胜利结算会跑两遍（遗物触发两次） |
| 以为"能 `clear()` 的集合一定是可变的" | `CardLibrary.MULTIPLAYER_STYLE` 是 `Set.of(...)`（不可变），数据包覆盖层做"整体还原"时 `clear()` 当场抛 `UnsupportedOperationException`（**只在运行时**，编译期看不出来）。给某张表加"快照/还原"能力前先确认它是 `LinkedHashSet`/`LinkedHashMap` |
| 只跑 `run-checks.ps1` 就以为验的是新代码 | 引擎自检会**自己重编** `combat/core`，但 22 套 MC 套件用的是 **gradle 产物** `build/classes/java/main`。改了主源码却不 `gradlew compileJava compileTestJava`，套件跑的是**上一次的 class**（我因此对着已修好的 `clear()` 又看了一遍栈）。**改完主源码先编译再跑套件** |
| 用 `Set-Content -Encoding ASCII` 改 `gradle.properties` | 它会把整个文件**重写成 ASCII**：中文注释全变 `?`、连行尾也被合并（v0.5.5.1 我为了让版本号从 0.5.5.0 变 0.5.5.1 这么干了一次，文件当场被毁，只能整份重写）。**改这一行用 edit 工具**（或 `-Encoding UTF8`，但仍要留意 BOM） |
| 把"正在拖动的牌"留在原槽位 | 手牌是**每帧全量重画**的，拖动时那张牌同时被画在槽位与鼠标上 —— 看起来像"两张牌"。要按 `dragCard` / 长按进度**跳过**原槽位，松手时清拖动状态自然回到原位（v0.5.5.1 用户反馈） |

## 8. 协作建议（给用户）

* **新会话 + 一轮一批（3 张）** 是真正的加速；"一轮十张"会让失败概率上升、反而更慢；
* 外部资料**直接贴文本**给我最省余量（抓网页很贵且常拿到空壳）；
* 长清单我会写进 `docs/`，聊天里只给结论。
